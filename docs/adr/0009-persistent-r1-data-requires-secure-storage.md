# Persistent R1 data requires secure Creation storage

An R1 may persist a Device grant, one target-bound Draft, a minimized 24-hour snapshot, and one minimal unresolved Controlled-command receipt only through versioned secure Creation storage. The receipt contains commandId, command kind, target identities, target turn for Stop, state, and timestamps, but no prompt, transcript, timeline, or tool payload. Recovery reconciles the receipt before enabling another Controlled command. Without secure storage, a distributable read-only product may operate session-only and require authorization and synchronization again after restart, but Follow-up and Stop do not ship; the client never falls back to localStorage. Unpairing, authentication invalidation, schema failure, or loss of a security capability wipes sensitive local state, while the daemon retains authoritative deduplication and audit results.
